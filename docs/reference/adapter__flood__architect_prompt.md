Protocol Architecture and the Gateway Service PatternThe fundamental architectural identity of Flood is that of a Backend-for-Frontend (BFF) or, more accurately in this context, a Protocol Gateway. It is a Node.js-based service that sits between the client (the browser or extension) and the torrent daemon. This positioning is not passive; Flood maintains its own internal model of the torrent session state, effectively decoupling the frontend's view of data from the backend's raw output.1.1 The Middleware Abstraction LayerAt the core of Flood's design is the clientGatewayService 1, a monolithic service orchestrator responsible for routing incoming API requests to the appropriate client adapter. When the 'CTRL' extension issues a request—for example, to add a torrent via URL—it does not speak to qBittorrent or rTorrent directly. Instead, the request follows a specific trajectory:Ingress: The HTTP request hits the Express.js / Fastify server layer.Validation: The payload is scrutinized against strict Zod schemas defined in the shared codebase. If the payload fails validation, the request is rejected immediately with a 422 status code, never reaching the torrent client.Routing: Validated requests are passed to the active client adapter (e.g., RTorrentClient, QBittorrentClient).Translation: The adapter translates the normalized Flood command into the specific protocol required by the daemon (e.g., converting a JSON object into an XML-RPC method call for rTorrent).Execution & Normalization: The daemon executes the command and returns a raw response. The adapter then normalizes this response back into a standard Flood object model before returning it to the client.Implication for 'CTRL': This architecture implies that the extension is interacting with a sanitized model, not the raw daemon. Features available in the raw daemon API may be inaccessible if Flood has not explicitly mapped them in the adapter layer. Conversely, Flood may polyfill features (like specific tag management logic) that the underlying daemon does not natively support in the same way.1.2 The Client Adapter PatternThe versatility of Flood lies in its modular adapter system. Each supported backend has a dedicated directory in the source tree (e.g., server/services/[client]/) containing the logic for protocol negotiation.2rTorrent Adapter: This adapter manages communication via SCGI (Simple Common Gateway Interface). It supports both the legacy XML-RPC protocol and the newer, more performant JSON-RPC protocol.3 The adapter is responsible for serializing requests into the appropriate format. Notably, it handles the quirks of rTorrent's specific data types, such as the recent fix for xmlrpc int type handling 3, ensuring that integers don't overflow or misbehave during serialization.qBittorrent Adapter: This acts as an HTTP client wrapper. Since qBittorrent uses a WebAPI, the Flood adapter must manage its own session cookie jar to authenticate with qBittorrent. It maintains a persistent connection to the torrent daemon to monitor health and activity. However, regarding the frontend, it employs a reactive state model. The frontend (and by extension, 'CTRL') is expected to maintain a local store of the torrent list. Flood pushes "diffs" or "patches" to this store.This design is critical for bandwidth efficiency. Instead of sending the full list of 5,000 torrents every second, Flood calculates what has changed (e.g., download speed updates for 5 active torrents) and sends only those changes. The extension architecture must therefore include a patch application engine capable of merging these diffs into its local state. Failing to do so will result in a "frozen" UI where the extension displays stale data.2.
