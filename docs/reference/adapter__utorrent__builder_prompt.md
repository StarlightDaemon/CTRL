Executive Summary and Architectural ScopeThe development of the "CTRL" browser extension requires a sophisticated integration strategy with the µTorrent Web API, a proprietary HTTP interface that enables remote management of the µTorrent client. Unlike modern, documentation-first APIs that adhere strictly to RESTful standards (Representational State Transfer), the µTorrent WebUI operates on a functional, query-string-based architecture that evolved organically alongside the desktop client. This report provides a comprehensive technical analysis of the API's surface area, specifically addressing the implementation of high-complexity features such as the RSS downloader, granular file prioritization, and delta-encoded state synchronization.The architectural challenge for the "CTRL" extension lies not merely in sending commands but in maintaining a coherent, synchronized state with the host client. The µTorrent API utilizes a unique Token-based authentication handshake that requires HTML parsing, a "Cache ID" system for bandwidth-efficient state updates, and a bitwise status flagging system that obscures the true state of torrent jobs behind integer masks. Furthermore, critical subsystems like the RSS filter manager are largely undocumented in public repositories, requiring the reverse-engineering of URL parameters and payload structures to achieve functional parity with the desktop GUI.This document serves as the definitive reference for the "Builder" implementation phase. It dissects the request/response cycles for every required feature, maps the obscure array indices returned by the server, and provides the algorithmic logic necessary to interpret the client's raw data into user-facing information. The scope extends to filling identified gaps in Settings Management, Feed Automation, and Per-Torrent Bandwidth allocation, ensuring the extension operates as a robust, fully-featured remote controller.2. Authentication Protocol and Session SecurityThe foundation of the "CTRL" extension's stability is its ability to establish and maintain an authenticated session. The µTorrent WebUI employs a dual-layer security model combining HTTP Basic Authentication with a custom token-based Cross-Site Request Forgery (CSRF) protection mechanism. A failure to strictly adhere to this handshake protocol will result in immediate 400 Bad Request rejections, rendering the extension non-functional.2.1 The Challenge of the Initial HandshakeThe authentication process is not a single API call but a sequence of dependencies. The client cannot simply "log in" and receive a persistent API key. Instead, it must negotiate a session that relies on both a browser cookie and a dynamic token generated by the server's backend.2.1.1 HTTP Basic AuthenticationThe entry point to the API is protected by standard HTTP Basic Authentication. The extension must encode the user's credentials (username and password) into a Base64 string. This string is transmitted in the Authorization header of the initial HTTP GET request.Header Construction: Authorization: Basic <Base64(username:password)>Target Endpoint: http://<IP>:<PORT>/gui/token.htmlIt is critical to note that the extension should not target the root /gui/ endpoint for the initial handshake, but specifically /gui/token.html.1 Targeting the root may trigger a standard interface load which is unnecessary for an API client and consumes additional bandwidth.2.1.2 The Token Extraction ParserUpon successfully passing the Basic Authentication check, the server returns an HTTP 200 response. However, the payload is not JSON. It is an HTML document containing a dynamic token embedded within a specific DOM element. The extension must implement a lightweight parser to extract this string, as it is required for every subsequent state-modifying request.The server response typically follows this structure:HTML<html>
  <div id='token' style='display:none;'>access_token_string_here</div>
</html>
The implementation logic must:Execute the GET request to /gui/token.html.Capture the response body as text.Parse the HTML to locate the div with id="token".Extract the inner text of this div. This is the Session Token.12.1.3 The GUID Cookie DependencySimultaneous to the HTML response, the µTorrent server sets a specific HTTP cookie named GUID. This cookie represents the unique session identifier. In a browser environment, this cookie is typically handled automatically by the browser's networking stack. However, if the "CTRL" extension operates in a context where cookie management is manual (e.g., a background service worker or a non-browser environment), this cookie must be explicitly captured from the Set-Cookie header of the token.html response and attached to the headers of all future requests.Critical Constraint: The API requires both the GUID cookie in the header and the ?token= parameter in the URL query string. If the cookie matches the session associated with the token, the request is authorized. If either is missing or mismatched, the server rejects the request.12.2 Session Persistence and Re-AuthenticationThe authentication token is not valid indefinitely. It is tied to the uTorrent client's runtime session and may expire after a period of inactivity or if the client is restarted. The "CTRL" extension must implement an "Auth-Retry" interceptor pattern.Monitor: Watch for HTTP 400 or 401 responses on standard API calls (e.g., ?list=1).Intercept: Pause the pending request queue.Re-Authenticate: Trigger the /gui/token.html flow to acquire a new token and GUID.Retry: Update the queued requests with the new token and re-send.This mechanism ensures the extension recovers gracefully from server restarts without requiring user intervention.3.
