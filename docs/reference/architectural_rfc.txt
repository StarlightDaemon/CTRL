Architectural & Security RFC: CTRL (Torrent Control Reloaded) – Expansion & Hardening Strategy1. Executive SummaryThis Request for Comments (RFC) delineates a comprehensive architectural strategy for the next major iteration of CTRL (Torrent Control Reloaded). As a cross-browser extension operating within the strict confines of Manifest V3 (MV3), CTRL faces a unique convergence of challenges: the deprecation of persistent background pages, the enforcement of rigorous Content Security Policies (CSP), and the increasing hostility of the browser environment toward local network requests. This report provides a deep-dive analysis and implementation roadmap across three critical vectors: Security Hardening, Feature Expansion, and Architectural Optimization.The transition to Manifest V3 is not merely a syntactic update but a paradigm shift that demands a "Zero Trust" architecture. The traditional extension model—relying on persistent background pages and broad host permissions—is obsolete. This document proposes a radical restructuring of CTRL’s security model, moving from plaintext storage to a client-side encrypted vault using the Web Crypto API, and replacing the invasive <all_urls> permission with granular, user-initiated Protocol Handlers and ActiveTab authorizations.Furthermore, the feature expansion strategy must navigate a volatile external ecosystem. The recent deprecation of Real-Debrid’s instant availability APIs necessitates a fundamental redesign of the user experience for cached downloads. Simultaneously, the integration of high-traffic but technically hostile trackers like TorrentGalaxy requires sophisticated DOM isolation techniques to protect the user interface from clickjacking and script injection.Finally, architectural optimization focuses on mitigating the performance bottlenecks inherent in managing large datasets within a React-based interface. By implementing TanStack Virtual for list virtualization and leveraging the Offscreen API to circumvent Service Worker termination, CTRL can achieve native-app responsiveness while adhering to the ephemeral nature of the MV3 environment. This report synthesizes findings from 188 research snippets to provide an exhaustive blueprint for building a secure, performant, and feature-rich torrent management suite.2. Security Hardening: The Zero-Trust Extension ModelThe current security posture of CTRL, while functional, reflects a legacy approach to extension development. Storing credentials in chrome.storage.local in plaintext and requesting global web access creates a significant attack surface. In the modern threat landscape, where browser extensions are high-value targets for supply-chain attacks and local malware, we must adopt a defense-in-depth strategy. This section details the cryptographic and architectural changes required to harden CTRL against both local and remote threats.2.1 Credential Storage & Encryption StrategyThe protection of sensitive user data—specifically the URLs, usernames, and passwords for remote torrent clients—is paramount. Current implementation relies on chrome.storage.local, which persists data as unencrypted JSON files on the user's filesystem. This creates two distinct vulnerabilities:Local Extraction: Any malware running on the user's machine with file read access can extract credentials from the browser’s profile directory.1Context Compromise: If the extension context is hijacked via Cross-Site Scripting (XSS), the attacker can trivially query the storage API to exfiltrate secrets.To mitigate these risks, we propose an "Encrypted Vault" architecture that leverages the browser's native cryptographic primitives.2.1.1 Cryptographic Primitives and Key DerivationWe will utilize the Web Crypto API (crypto.subtle) to implement client-side encryption. Since MV3 Service Workers cannot securely persist encryption keys (as they are ephemeral and have no secure storage of their own), we must derive the key from a user-provided secret (a "Master Password") at runtime.The chosen algorithm for key derivation is PBKDF2 (Password-Based Key Derivation Function 2).2 While newer algorithms like Argon2 offer better resistance to GPU-based cracking, they require WebAssembly, which introduces complexity and potential CSP friction in MV3.3 PBKDF2 is natively supported by the browser and provides sufficient security when configured correctly.Key Derivation Parameters:Algorithm: PBKDF2 using SHA-256 as the HMAC hash function.Iterations: A minimum of 100,000 iterations is recommended to increase the computational cost of brute-force attacks.4 However, given the ephemeral nature of Service Workers, we must balance this against startup latency. A configurable iteration count (defaulting to 300,000) provides a robust margin of safety.Salt: A unique, random 16-byte salt must be generated for each user upon vault creation and stored in plaintext in chrome.storage.local. This prevents rainbow table attacks.5Vault Encryption:Once the cryptographic key is derived, it is used to encrypt the credential payload. We will use AES-GCM (Advanced Encryption Standard in Galois/Counter Mode). AES-GCM is an authenticated encryption algorithm, meaning it ensures both the confidentiality of the data (it cannot be read) and its integrity (it cannot be modified without detection).IV (Initialization Vector): A unique 12-byte IV must be generated for every encryption operation. Reusing an IV with the same key in GCM mode is a catastrophic security failure.Storage: The resulting ciphertext and the IV are stored in chrome.storage.local. The derived key itself is never stored on disk.2.1.2 The Service Worker "Amnesia" ChallengeA critical challenge in Manifest V3 is that the Service Worker (SW) is event-driven and terminates after roughly 30 seconds of inactivity.6 In a standard web app, the decrypted key might be held in a global variable. In MV3, when the SW wakes up to handle a background event (e.g., checking torrent progress), any global variables are lost.If we relied solely on memory, the user would be forced to re-enter their Master Password every time the extension woke up, which is UX suicide. Conversely, storing the key in chrome.storage.local defeats the purpose of encryption.The Solution: chrome.storage.sessionThe chrome.storage.session API provides a secure middle ground.7Scope: Data stored in the session area is held in memory by the browser process. It is not written to disk.Persistence: It persists as long as the browser session is active, surviving Service Worker terminations and restarts.Security: It is accessible only to the extension context, protecting it from other processes or extensions.Operational Workflow:Unlock: The user enters their Master Password in the popup. The UI thread derives the CryptoKey.Export: The key is exported to a raw format (e.g., via crypto.subtle.exportKey) because structured cloneable objects like CryptoKey cannot always be directly stored in the storage API depending on browser implementation nuances.Persist: The raw key material is stored in chrome.storage.session.Wake-Up: When the Service Worker starts (e.g., triggered by an alarm), it retrieves the raw key from chrome.storage.session.Import: The SW imports the raw key back into a usable CryptoKey object via crypto.subtle.importKey.Decrypt: The SW fetches the encrypted credentials from chrome.storage.local, decrypts them, and performs the necessary API calls.This architecture ensures that sensitive credentials exist in plaintext only within the volatile memory of the extension process and only while the user's browser session is active.2.2 Permission Scoping: The Shift from <all_urls>The current requirement for <all_urls> permission allows CTRL to inject content scripts into every page to scan for magnet links. This is a "sledgehammer" approach that triggers severe privacy warnings during installation ("Read and change all your data on the websites you visit").8 To improve user trust and security hygiene, we must transition to a model of granular, intent-based permissions.2.2.1 Leveraging Native Protocol HandlersThe most effective way to handle magnet links without broad permissions is to register CTRL as the system-wide or browser-wide handler for the magnet: protocol.The protocol_handlers Manifest Key:Manifest V3 supports the protocol_handlers key, which allows the extension to register itself to handle specific URL schemes.9JSON"protocol_handlers":
When configured, clicking a magnet link—whether in a browser tab, a chat application, or a PDF—triggers the browser to launch the extension's handler page (handler.html) with the magnet URI passed as a query parameter.Advantages:Zero Permissions: This mechanism requires no host permissions. The extension does not need to read the web page; it simply receives the link passed by the browser.Privacy: The extension is only aware of the specific link the user clicked, not the user's browsing history or page content.User Intent: The action is initiated by an explicit user gesture (the click), aligning with the MV3 philosophy of user agency.11Limitations & Mitigations:Browser Support: While web+ schemes are widely supported, magnet is a safelisted scheme in Chrome and Edge but may have varying behavior in Firefox or on specific OS configurations (e.g., Linux xdg-open handlers).12UX Friction: The browser may prompt the user to confirm the handler registration. We must implement an onboarding flow that guides the user to accept this permission.2.2.2 The activeTab Permission StrategyFor scenarios where the protocol handler is not viable (e.g., text selection or context menus), the activeTab permission serves as a powerful alternative to <all_urls>.13The activeTab permission grants the extension temporary access to the currently active tab only when the user invokes the extension (e.g., via a toolbar click, context menu interaction, or keyboard shortcut). This access includes the ability to inject scripts and read the URL/title, but it expires as soon as the user navigates away or closes the tab.Context Menu Implementation:We will implement a context menu item: "Download with CTRL".User Action: User right-clicks a link or page background.Trigger: The contextMenus API fires an event.Permission Grant: Chrome implicitly grants activeTab permission for that specific tab.Execution: The extension injects a lightweight content script to parse the selection or link and sends it to the torrent client.This approach eliminates the install-time warning entirely, as permissions are granted dynamically and contextually.2.2.3 Optional Host Permissions for Site IntegrationsFor the "Site Integrations" module (1337x, Nyaa, etc.), we cannot rely on activeTab because these modules often require automatic script injection to modify the DOM (e.g., adding "Download" buttons). However, not all users use all sites.We will utilize the optional_host_permissions manifest key.15Default State: The extension installs with no host permissions.Opt-In Flow: In the CTRL settings dashboard, the user toggles "Enable 1337x Integration".Request: The extension calls chrome.permissions.request({ origins: ['*://1337x.to/*'] }).Grant: The browser prompts the user to allow access specifically for that domain.This implements a "Least Privilege" model where users only grant access to the specific sites they frequent, rather than the entire web.2.3 Content Script Isolation & UI ProtectionInjecting User Interface (UI) elements, such as "Add to CTRL" buttons or status overlays, into third-party websites presents significant security and stability risks. Pirate sites and torrent indexers are notoriously hostile environments, often laden with aggressive scripts, ad overlays, and anti-scraping measures. A hostile page could hijack our UI events (clickjacking), spy on user interactions, or break our styling via CSS leakage.2.3.1 Shadow DOM for EncapsulationTo protect the CTRL UI from the host page's CSS and accidental interference, we must encapsulate all injected elements within a Shadow DOM.17Implementation Detail:Mode 'Closed': We will create the shadow root with { mode: 'closed' }. This prevents the host page's JavaScript from accessing the shadow root via the shadowRoot property of the host element, adding a layer of obfuscation (though not perfect security).19CSS Isolation: Styles defined inside the Shadow DOM do not leak out, and global page styles (like a generic button { display: none }) do not penetrate in. This ensures our UI looks consistent regardless of the site's chaos.Event Retargeting: Events originating from within the Shadow DOM are retargeted to the host element. This obscures the internal structure of our UI from the host page, making it harder for scripts to distinguish between a click on "Download" versus "Cancel".2.3.2 Execution Worlds: Main vs. IsolatedChrome Extensions invoke content scripts in an "Isolated World".20 This means the extension's JavaScript shares the DOM with the page but has a separate execution context. Variables defined by the page (e.g., window.jQuery) are invisible to the extension, and vice versa. This prevents the host page from overriding native prototypes (like Array.prototype.push) to attack the extension.However, complex integrations (like scraping TorrentGalaxy) often require access to data stored in the page's JavaScript context (the "Main World").Strategy: We will strictly separate logic.UI Logic: Runs exclusively in the Isolated World. It handles button clicks, messaging with the background script, and DOM manipulation.Data Scraping: If deep data extraction is needed (e.g., reading a global torrentHash variable), we will use chrome.scripting.executeScript with world: 'MAIN' to extract the data and pass it back via a custom DOM event or window.postMessage.Validation: Any data received from the Main World must be treated as untrusted user input and rigorously sanitized before use to prevent XSS.2.3.3 Iframe Sandboxing for Complex UIFor more complex interfaces, such as a "Mini Dashboard" overlay that shows download progress, injecting DOM elements is too risky. The host page can still interfere with layout or overlay elements on top.The Iframe Solution:We will inject an iframe whose src points to a resource within the extension package (chrome-extension://<id>/overlay.html).Security Boundary: This treats the UI as a Cross-Origin resource. The host page cannot access the DOM of the iframe, nor can it read its cookies or storage.Communication: Communication between the host page content script and the iframe occurs via window.postMessage. We must validate the origin of every message to ensure it comes from our extension context.2.4 CSP Strategy & Local Network Access (LNA)Connecting to a user's local torrent client (e.g., http://127.0.0.1:8080 or http://192.168.1.50:9091) poses unique challenges in the modern web platform, specifically regarding Content Security Policy (CSP) and the upcoming Local Network Access (LNA) enforcement.2.4.1 Content Security Policy (CSP) ConfigurationManifest V3 enforces a strict default CSP. We must define a policy that allows necessary connections while blocking everything else to mitigate Cross-Site Scripting (XSS) risks.Proposed CSP:HTTPcontent_security_policy: {
  "extension_pages": "default-src 'self'; connect-src 'self' http://localhost:* http://127.0.0.1:* ws://localhost:* ws://127.0.0.1:*; img-src 'self' data: https:; object-src 'none';",
  "sandbox": "..."
}
connect-src: We explicitly allow localhost and 127.0.0.1 for local clients. Note that we cannot wildcard local network IPs (like 192.168.*.*) in the manifest CSP easily. The browser typically allows connections to arbitrary IPs if they are requested via the fetch API from the background context, but the CSP restricts what extension pages (like the popup) can load directly.script-src: MV3 mandates 'self', disallowing remotely hosted code. This is non-negotiable and requires us to bundle all dependencies.2.4.2 Navigating Local Network Access (LNA) RestrictionsChrome is actively rolling out Local Network Access (LNA) protections (formerly Private Network Access).21 This security feature blocks public websites (and potentially extensions) from making requests to private IP addresses (RFC1918) to prevent CSRF attacks against local devices (e.g., routers).The Challenge:Starting in Chrome 138+, requests to private IPs may be blocked or require a "Preflight" OPTIONS request that the target server (the torrent client) must respond to with specific headers (Access-Control-Allow-Private-Network: true). Most torrent clients do not support these headers yet.The Extension Exemption Strategy:Current Chromium documentation implies that extensions are exempt from LNA checks if they declare the target host in their host_permissions.23Detection: The extension must allow the user to input their client URL (e.g., http://192.168.1.50).Dynamic Permission Request: Upon saving this URL, CTRL must programmatically call chrome.permissions.request({ origins: ['http://192.168.1.50/*'] }).User Grant: The user confirms this permission.Exemption: With this explicit permission, the browser recognizes the user's intent and should bypass the LNA block, allowing the fetch request to proceed without the server needing to support the new CORS headers.Mixed Content Considerations:If the extension relies on a background page (Service Worker), it runs in a secure context. Connecting to http:// (insecure) local IPs might trigger "Mixed Content" blocking. However, http://127.0.0.1 is considered a "Potentially Trustworthy Origin" and is exempt. For 192.168.x.x addresses, users may need to configure Chrome flags or, ideally, we should encourage the use of self-signed HTTPS certificates for their torrent clients, although this adds significant friction.3. Feature Expansion: High-Value IntegrationsThe "Reloaded" mandate implies not just maintenance but significant evolution of the product's capabilities. This section outlines the integration of premium Debrid services and high-traffic indexers, addressing specific technical hurdles discovered during research.3.1 The Debrid Module: Real-Debrid & AllDebridDebrid services fundamentally alter the torrenting workflow by acting as a high-speed caching proxy. Instead of joining a swarm, the user requests a file from the Debrid service. If cached, it is served instantly via HTTP; if not, the Debrid service downloads it on the user's behalf.3.1.1 The Real-Debrid API CrisisResearch 24 indicates a critical breaking change in Real-Debrid's ecosystem: the /torrents/instantAvailability/{hash} API endpoint, historically used to check if a torrent is cached before adding it, has been deprecated or rendered unreliable to prevent scraping abuse. This forces a fundamental redesign of the proposed "Check Cache" feature.Revised "Blind Add" Architecture:We cannot reliably promise the user "Instant Download" before they click. We must adopt a reactive workflow:Action: User clicks "Download with Real-Debrid".API Call: CTRL sends the magnet link directly to /torrents/addMagnet.25Polling: The extension monitors the torrent status via /torrents/info/{id}.State Handling:Status: waiting_files_selection: This is the critical juncture. The API requires the user to select which files to download to activate the torrent.Automation: CTRL will automatically fetch the file list and select the largest video file (or all files, based on user preference) via /torrents/selectFiles/{id}.25Status: downloaded: If the status jumps immediately to downloaded after file selection, the item was cached. CTRL notifies the user: "Ready for Stream/Download".Status: downloading: If it enters the downloading state, it is uncached. CTRL notifies: "Queued on Debrid Cloud".This "Fire and Optimise" approach ensures functionality despite the API degradation, prioritizing user convenience (auto-selection) over pre-add information.3.1.2 AllDebrid IntegrationIn contrast, AllDebrid appears to maintain support for /magnet/instant.27Differentiation: We can offer a superior UX for AllDebrid users by implementing real-time cache checking.Mechanism: When a user visits a supported tracker, CTRL extracts all magnet hashes on the page and batches them into a single request to AllDebrid's instant availability endpoint.UI Feedback: Available torrents are highlighted with a green "Instant" icon, providing a tangible value-add for AllDebrid subscribers.3.2 Site Integrations: Tackling Hostile DOMs3.2.1 TorrentGalaxy (TGx)Profile: TorrentGalaxy is currently one of the highest-traffic trackers, filling the void left by RARBG. It is characterized by a chaotic UI, aggressive popunders, and robust anti-bot protection (Cloudflare + CAPTCHA).29Scraping Strategy: User-Assisted InjectionDirectly fetching TGx pages from the background Service Worker will fail due to Cloudflare challenges (403 Forbidden or 503 Service Temporarily Unavailable). We must rely on the user's active tab.Content Script: A content script runs on torrentgalaxy.to.State Detection: The script detects if the user is in a "Verified" state (post-CAPTCHA).DOM Sanitization:The script creates a Shadow DOM overlay to inject "Clean Mode" controls.It identifies the magnet link element (typically an <a> tag with href^="magnet:").Ad Stripping: Using CSS injection (via chrome.scripting.insertCSS), we hide known ad containers and overlays that obscure the magnet links.Action: When the user clicks the CTRL button, the magnet is extracted from the DOM and passed to the background worker via runtime.sendMessage.3.2.2 YTS / YIFYProfile: The dominant source for movie torrents.Feasibility: High. YTS offers a public, documented API (yts.mx/api/v2).30Integration Plan:Metadata Injection: When the user visits a YTS movie page, CTRL can query the YTS API using the IMDb ID found in the page metadata.Value Add: The API returns peer counts and "quality" availability (720p/1080p/4K). We can inject a "Quick Quality Select" dropdown directly into the page, allowing the user to send a specific quality release to their client without navigating to the specific torrent page.Dead Torrent Warning: We can gray out quality options that have 0 seeds as reported by the API, saving the user from stalled downloads.4. Architectural Optimization & UXThe transition to Manifest V3 introduces strict resource constraints. The "Background Page" is dead, replaced by the ephemeral Service Worker. This section addresses the two most significant engineering challenges: maintaining high-performance rendering for large torrent lists and keeping the extension "alive" for long-running tasks.4.1 React Performance: High-Frequency UpdatesThe Problem: The core "Torrent Control" dashboard displays a list that may contain thousands of torrents. Clients like qBittorrent report updates (speed, progress, peers) every 1-2 seconds. Naively re-rendering a React component tree of 2,000+ complex rows every second will flood the main thread, causing UI lag and battery drain.31Solution: Virtualization & Fine-Grained Reactivity4.1.1 TanStack Virtual (v3)We will implement TanStack Virtual to handle list rendering.32Concept: Instead of creating 2,000 DOM nodes, the virtualizer calculates the total height of the list but only renders the items currently visible in the viewport (plus a small "overscan" buffer). This reduces the DOM footprint from thousands of elements to ~20-30.Dynamic Heights: Torrent rows often vary in height (e.g., expanding to show file details). TanStack Virtual supports dynamic measurements via the measureElement API.34Challenge: Dynamic measurement can cause "scroll jitter" if measurements change while scrolling upwards.36Mitigation: We will implement a Hybrid Sizing Strategy. The collapsed row state will have a strictly enforced fixed height (e.g., 60px). We will only enable dynamic measurement for expanded rows. This stabilizes the scroll physics for the majority of interactions.4.1.2 The "Data Grid" State PatternTo prevent the "Prop Drilling" problem where a global state update triggers a re-render of every row, we will decouple the data fetching from the row rendering.Normalized Store: We will use a state manager like Zustand or TanStack Query to store torrent data in a normalized map (Key: Hash -> Value: Data), rather than an array.Selector Optimization: The <TorrentList> component will only render a list of IDs.Component Isolation: Each <TorrentRow id={hash} /> will connect individually to the store using a selector hook: const torrent = useStore(state => state.torrents[hash]).Equality Checks: React's reconciliation engine will ensure that if a specific torrent's data hasn't changed (e.g., a paused torrent), its component does not re-render, even if other torrents in the list have updated.4.2 Background Persistence: Solving the 30-Second DeathThe Problem: MV3 Service Workers are designed to die after 30 seconds of idleness. If CTRL is polling a torrent client to detect a finished download (to send a notification), the SW will terminate, the polling stops, and the notification is never sent.6Solution: The Offscreen Document PatternWe will implement the Offscreen API (chrome.offscreen) as a legitimate mechanism to maintain a persistent heartbeat for critical tasks.394.2.1 The KeepAlive MechanismInitialization: When the extension detects an active operation (e.g., a download is in progress), it creates an offscreen document.JavaScriptawait chrome.offscreen.createDocument({
  url: 'offscreen.html',
  reasons:, // Justification: blob processing or similar valid reason
  justification: 'Maintaining connection for active download monitoring'
});
The Heartbeat Loop: Inside offscreen.html, a script runs a setInterval loop (e.g., every 20 seconds).Messaging: The script sends a message to the Service Worker: chrome.runtime.sendMessage({ type: 'keepAlive' }).Lifecycle Extension: The receipt of this message resets the Service Worker's idle timer, keeping it alive for another 30 seconds.41Teardown: Crucially, to be good citizens of the browser ecosystem, we must destroy the offscreen document (chrome.offscreen.closeDocument) as soon as the download finishes. We should not keep the SW alive indefinitely when the extension is idle.4.2.2 Fallback: The Alarms APIFor less critical tasks (e.g., checking RSS feeds once per hour), we should not use the KeepAlive pattern. Instead, we use the chrome.alarms API.41Behavior: An alarm acts as a system wake-up call. When the alarm fires, the browser wakes up the Service Worker, executes the task, and then allows it to go back to sleep.Optimization: This is the preferred method for periodic background syncs as it has zero impact on battery life between intervals.5. ConclusionBy adopting this architectural strategy, CTRL evolves from a simple utility into a hardened, enterprise-grade application. We trade the convenient but dangerous <all_urls> permission for a secure, user-centric model based on protocol_handlers and explicit consent. We acknowledge the volatility of the MV3 Service Worker but engineer around it using sanctioned APIs like offscreen and alarms. Finally, we proactively adapt to the degradation of the Real-Debrid API, ensuring that CTRL remains the most reliable and sophisticated torrent management suite in the browser ecosystem. The result is a product that respects user privacy, protects their credentials, and performs flawlessly under heavy load.
