Architectural Analysis of Aria2 JSON-RPC Protocol for Browser Extension Integration1. Executive Summary and Architectural ScopeThe integration of the Aria2 download utility into a modern browser environment—specifically within the constraints of a "CTRL" browser extension—requires a rigorous, architectural deconstruction of the Aria2 JSON-RPC interface. Aria2 stands as a distinct utility in the landscape of download managers due to its lightweight footprint, multi-protocol support (HTTP, HTTPS, FTP, SFTP, BitTorrent, Metalink), and its ability to function as a daemonized backend controlled remotely via RPC.1 However, the bridge between a browser-based frontend (executing JavaScript within a secured sandbox) and a local system daemon (aria2c) introduces significant complexity regarding protocol synchronization, security boundaries, and transport stability.This report serves as a definitive architectural guide for the implementation of the Aria2Adapter. It moves beyond surface-level API documentation to analyze the underlying behaviors of the daemon, the precise mechanics of the JSON-RPC 2.0 implementation, and the critical "edge cases" that arise when interfacing with the file system asynchronously. The analysis focuses heavily on the requirements of the "CTRL" extension, particularly the necessity of an event-driven architecture using WebSockets to maintain real-time state without the overhead of HTTP polling.Key findings detailed in this report include the critical distinction between transport layers where HTTP lacks the notification capabilities essential for a reactive UI 3; the non-standard token injection syntax required for authentication which deviates from typical header-based auth 3; and the strict security implementations in Aria2 version 1.36.0 regarding TLS 1.3 that may break compatibility with older self-signed certificate configurations.5 Furthermore, we examine the "Ghost Download" phenomenon—where file system state diverges from daemon memory state—and propose rigorous reconciliation strategies.4 The following sections provide an exhaustive technical breakdown of these components.2. Transport Layer ArchitectureThe fundamental architectural decision in designing the Aria2Adapter is the selection of the transport layer. Aria2 exposes its JSON-RPC interface over two primary transports: HTTP and WebSocket. While both adhere to the JSON-RPC 2.0 specification, their operational characteristics differ radically, influencing the extension's performance, battery usage (on laptops), and code complexity.2.1. HTTP Transport Protocol AnalysisThe HTTP transport in Aria2 is implemented as a standard POST endpoint, typically accessible at http://localhost:6800/jsonrpc.4 It strictly follows the request-response model defined in HTTP/1.1.2.1.1. Statelessness and Polling OverheadIn the context of the "CTRL" extension, which aims to visualize download progress (speed, percentage, peers) in real-time, the stateless nature of HTTP presents a significant bottleneck. Every update to the UI requires a new request. To achieve a smooth 60fps or even 1fps update rate, the extension must issue aria2.tellActive and aria2.tellWaiting commands repeatedly.Network Overhead: Each polling cycle involves the full TCP handshake (SYN, SYN-ACK, ACK) unless Keep-Alive is successfully negotiated and maintained.6 Even with persistent connections, there is header overhead for every request and response.Latency Accumulation: In high-latency loopback scenarios (e.g., heavy CPU load), the "request-process-response" cycle introduces lag. If the user pauses a download, the UI will not reflect this state until the next poll resolves.Resource Exhaustion: Rapid polling can exhaust ephemeral ports on the host machine if connections are not properly reused, leading to EADDRNOTAVAIL errors.2.1.2. The Notification GapThe most critical architectural deficit of the HTTP transport for this use case is the complete absence of server-initiated notifications. The Aria2 documentation explicitly states that "The JSON-RPC interface does not support notifications over HTTP".4Implication: Events such as onDownloadStart, onDownloadComplete, or onBtDownloadComplete are never pushed to the HTTP client.State Inference: The client must infer state changes by comparing the results of sequential polling requests. For example, if a GID present in the "Active" list during Poll N is missing in Poll N+1, and appears in the "Stopped" list, the client infers completion. This logic is brittle, prone to race conditions, and computationally expensive for the browser extension to maintain.2.2. WebSocket Transport Protocol AnalysisThe WebSocket transport is implemented as an extension to the internal HTTP server of Aria2.4 It operates on the same port (default 6800) and upgrades the connection via the standard HTTP Upgrade: websocket header mechanism.42.2.1. Persistent Bidirectional CommunicationUpon successful handshake, the WebSocket establishes a full-duplex TCP stream. This allows the Aria2 daemon to push data frames to the client without a preceding request.Efficiency: Once established, there is zero handshake overhead for subsequent commands. This makes it ideal for high-frequency commands or rapid state updates.Real-time Synchronization: The daemon pushes notification events immediately upon their occurrence within the internal event loop. This ensures the "CTRL" extension reflects the true state of the daemon with millisecond-level latency.2.2.2. JSON-RPC 2.0 Compliance and CorrelationAria2's implementation strictly adheres to JSON-RPC 2.0, utilizing the id field for message correlation.3Request Correlation: When the extension sends a command (e.g., addUri), it must include an id (string or integer). The daemon mirrors this id in the response object ({"jsonrpc": "2.0", "id": "my_id", "result":...}).Notification Distinction: Crucially, server-initiated notifications are distinguished by the absence of the id field.6 The extension's socket listener must implement logic to route messages with an id to the pending promise/callback handler, and messages without an id to the event dispatcher.2.3.
